# 부분 수정 품질 개선 — 실행 배정

사용자 승인: 팀별 작업을 배정하고 부분 수정 품질 개선부터 진행하며 총괄이 검토·통합한다. 추가로 GitHub에서 Codex 개발에 유용한 도구를 다운로드해 사용하도록 요청했다. 이 배정은 첫 온보딩의 읽기 전용 제한을 해당 범위에서 대체한다.

목표는 실제 SDXL 부분 수정의 지시 준수·형태 유지·경계를 개선하고 원본 밖 RGB/알파 및 기존 저장·후보·모션 경계를 보존하는 것이다. 신기능 확장·새 대형 모델·유료 API·외부 게시는 이번 범위에 넣지 않는다.

> 2026-10-23 2차 총괄 판정: 최초 Base 비교4회에서 수용 후보0개를 확인했다. 위의 새 모델 제외는 최초 비교 범위로 마쳤고, 사용자의 품질 개선 요청을 완결하기 위해 공식 `diffusers/stable-diffusion-xl-1.0-inpainting-0.1`의 **추가 FP16 UNet 약5.14GB 한 개**를 격리 시험하는 범위로 확장한다. 새 영구 모델 기본값/앱 그래프 변경은 전후 품질·자원 검증 후 결정한다. 무작위 파라미터 탐색·추가 모델 확대는 하지 않는다.

모든 담당은 자기 채팅에서 보고하고 자기 인계 파일에 남긴다. 총괄이 읽어 취합하며 담당끼리 메시지를 보낼 필요는 없다. 추가 채팅/하위 에이전트는 이 작은 작업에 늘리지 않는다. 외부 공개나 원격 저장소 변경을 하지 않는다.

## 실행 순서와 자원

1. 기존 source/mask/recipe/result를 먼저 확인한다. 동일 source/mask/seed의 기준 결과를 확보한 후 가설을 세운다.
2. GPU와 실제 API 작업은 **이미지 AI 담당이 독점**한다. 현재 설치된 SDXL Base를 사용한다. 최초 비교는 최대4회로 제한하고, 추가 실험이 필요하면 근거를 총괄에 보고한다.
3. 프론트·UX·편집·출시 담당은 GPU·공유 브라우저·앱 프로세스를 조작하지 않는다. QA도 첫 단계는 스크립트/근거 준비이며 실제 GPU 재현은 총괄이 순서를 바꿔 배정한다.
4. 원인과 최소 수정안을 총괄에 먼저 구체화한다. baseline 완료 뒤 관련 실패 테스트와 최소 수정을 진행한다. 새로운 하위 시스템이나 대형 모델 도입은 범위를 넓히지 말고 현재 근거를 보고한다.
5. 앱/Comfy 서버 재시작과 최종 web/index.html 빌드는 총괄이 수행한다. 제품 소스 변경 때문에 서버 guard가 달라지면 성공한 척 계속 실행하지 않는다.
6. 변경 후보가 준비되면 총괄이 파일/전후 이미지를 직접 검토하고 QA에 독립 수용을 배정한다. 품질 개선과 기능 보존의 증거를 분리한다.

## 필수 기록

원본·마스크·seed·모델/설정·실제 요청 prompt·workflow·job ID·시간·원본 밖 RGB/알파 오차·변경 영역·육안 품질을 대응시킨다. 캐시 적중은 새 추론으로 세지 않는다. 같은 조건의 baseline과 후보가 없으면 비교 개선을 주장하지 않는다. 합격하지 않은 결과와 한계도 보존한다.

품질 비평은 지시 반영, 의도하지 않은 형태 변화, 경계/재질, 캐릭터 특징 유지로 나눈다. 코드 테스트 통과만으로 이미지 품질 합격을 표시하지 않는다.

## 2차: 전용 inpaint 모델의 제한된 적합성 시험

- Mac 출시 담당: 공식 revision·LFS SHA·라이선스와 자원 비용을 고정하고 추가 UNet 한 파일만 프로젝트 안에 다운로드·검증한다. 기존 Base 가중치와 venv·셸·실행기는 바꾸지 않는다. 새 파일이 Comfy core UNETLoader에서 보이는 경로와 provenance를 기록한다.
- 이미지 AI 담당: 현재 core의 UNETLoader + InpaintModelConditioning과 기존 Base의 CLIP/VAE를 이용하는 명시적 실험 그래프를 작성한다. 최초 smoke1회와 같은 입력의 비교 최대2회로 제한하며 실제 실행 전 다운로드 검증과 GPU 이관을 확인한다. 앱 성공이나 양산 품질로 과장하지 않는다.
- 최초에는 모델 로드, MPS/메모리, NaN·회색·실패, sampler 실행, 밖 RGB/전체 alpha 보존,4축 품질을 함께 판정한다. 모델과 필수 conditioning이 결합된 방법 비교임을 밝힌다.
- 원본/마스크/seed/prompt/steps/CFG/denoise/sampler/scheduler를 가능한 한 고정하고 모델 방법만 바꾼다. 그래프 변경·원본 해시·checkpoint/UNet 두 파일 근거를 보존한다.
- 총괄의 실제 UI 검수1회가 끝날 때까지 AI의 추가 GPU 실행을 대기한다. 다른 담당은 다운로드·스크립트 준비·오프라인 QA를 병렬로 진행할 수 있다. 후보가 미달이면 앱에 적용하지 않고 실패와 다음 판단을 기록한다.

## 2026-10-23 총괄 판정

- GitHub 공식 Ruff 0.17.1 / ast-grep 0.51.0 설치·무결성·실제 사용을 완료했다. 재사용 명령은 `docs/DEV-TOOLS.ko.md`에 있다.
- 생성 스타일/전체 브리프가 부분 수정에 자동 합쳐지는 충돌과 모드별 안내를 수정·빌드했다. 총괄의 실제 브라우저 job과 QA의 독립 요청/픽셀 검증으로 수용했다.
- 최초 비교4회와 전용 모델 비교3회 모두 품질 미수용이다. 전용 UNet 파일 다운로드·실제 MPS 로드/실행은 검증했지만 앱 모델/기본값/제품 backend에는 채택하지 않았다. UX·QA·총괄의 실물 판정이 일치한다.
- 이미지 AI의 3회 한정 GPU 작업은 종료했고 여분 제출은 없다. 정밀 색 변경 품질은 미해결로 남기며, 현재 결과를 품질 개선 완료나 모델 일반 성능의 결론으로 표시하지 않는다.
