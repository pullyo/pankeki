# Pankeki 사용자 작업과 경쟁제품 흐름 비교

2026년 10월 20일 KST 확인 · 사용자·경쟁제품 리서치 1차 · 총괄 검토 대기

Pankeki가 도울 핵심 작업은 **오리지널 캐릭터의 조건을 정하고, 후보를 판단하고, 선택한 원본의 일부를 고쳐 다음 작업자가 이어갈 수 있게 남기는 것**이다. 후보 이력·부분 수정·프로젝트 저장은 비교 제품에도 있다. 따라서 기능 이름보다 요구 충족 여부와 선택 이유를 편집·저장까지 이어 주는 흐름을 검증할 가치가 있다. 현재 저장 결과에서는 이미지 생성 성공과 세부 요구 충족이 분리된다. 채팅은 미연결이며 실제 이미지 작업은 상세 설정에서 시작한다. 추가 우선 요청인 Live2D 아이디어는 [Live2D 편집 패턴](live2d-workflows.md)에 짧게 정리했다.

## 확인된 요구와 가설

| 구분 | 내용 | 근거와 해석 범위 |
| --- | --- | --- |

| 작업 가설 | 부위·원본·수정 목표가 함께 보이면 잘못된 후보나 영역을 고치는 실수가 줄어들 수 있음 | 소스의 상태 분리와 저장 화면을 근거로 한 추론. 실제 사용 오류가 발생했다는 주장은 아님 |

이 조사는 기존 사용자 결정의 인계 기록, 현재 소스, 저장된 실제 생성 결과와 화면, 공식 제품 문서에 근거한다. 인터뷰·설문·사용자 테스트는 수행하지 않았다. 공개 커뮤니티 글을 제품의 현재 기능이나 사용자 빈도 근거로 사용하지 않았다.

## 핵심 작업과 막히는 지점

| 작업 | 현재 가능한 흐름 | 관찰과 잠재적 막힘 | 영향과 확신 |
| --- | --- | --- | --- |
| 아이디어를 구체화 | 용도·브리프·외형·소품·팔레트·추가지시를 입력하고 실제 전달 문장 확인 | 주화면의 대화 전송은 비활성. 상세 설정 경로와 미연결 안내는 존재함 | 현재 연결 제약은 확정. 신규 사용자가 경로를 놓치는 빈도는 미측정 |
| 후보에서 다음 행동 결정 | 1~2장 생성, 두 후보 비교, 크게 보기, 이어서 수정 | 비교 캡션은 후보·출처·seed 중심. 필수 요구별 충족/미충족·선택 이유는 별도 구조가 없음 | 판단 지원 필요성은 강한 가설. 이미지 요구 실패 자체는 저장 증거로 확인 |
| 마음에 든 디자인의 한 부분만 변경 | 후보의 이어서 수정 → 원본 캔버스 → 수동 마스크 → 추가지시 → 새 자식 후보 | editCandidate는 원본을 바꾸지만 후보의 과거 brief/request로 현재 설정을 자동 교체하지 않음. 현재 지시와 과거 후보 조건이 다를 수 있음 | 기존 입력 보존이라는 장점이 있음. 잘못된 대상·지시 혼동은 검증할 위험 가설 |
| 수정 결과를 수락하거나 되돌림 | 원본 후보를 남기고 parentId로 자식 관계를 기록, 기존 두 후보 비교 재사용 가능 | 마스크 밖 픽셀 보존과 장갑 색·가방 재질 충족은 다른 판단. 자동 품질 판정은 없음 | 기술적 보존과 시각적 요구의 분리가 필요함. 품질 기록은 과거 실행 증거 |
| 작업을 저장하고 다시 시작 | JSON에 브리프·내장 이미지·계보·선택 기록, 브라우저 자동 저장, 보드 PNG | source/mask는 내보낸 request에서 제외. 불러오면 마스크 초기화·비교 선택 해제·txt2img 모드. 재칠하기 안내는 이미 있음 | 후보 복원과 편집 중간 상태 복원은 다름. 재개 비용의 실제 크기는 미측정 |
| 다음 작업자에게 전달 | 보드에 선택 이미지·설정·색·메모 출력 | 보드는 현재 프로젝트 brief를 사용함. 후보 생성 당시 brief와 다를 수 있으며, 기준 설명과 관찰 결과의 구분이 필요함 | 문서 불일치 가능성은 소스상 추론. 실제 전달 실패 사례는 없음 |

우선 판단 문제는 **필수 속성 누락을 놓친 채 완료로 판단하는 위험**, 다음은 **원본·수정 범위와 재개 상태를 혼동하는 위험**이다. 모든 항목의 사용자 발생 빈도는 아직 모른다. 이 순위는 고객 통계가 아니라 현재 목표에 미치는 영향과 저장 증거의 강도에 따른 조사 우선순위다.

## 이미지와 화면에서 확인한 범위

- 최신 `shutdown-checkpoint.md`는 SDXL 적용과 실제 SDK 생성 9회 완료를 명시한다. 이전 문서의 SDK 미구현·Turbo 기본값을 현재 사실로 재사용하지 않았다.
- 이번 담당은 저장된 B군 601020과 C군 3장의 PNG를 직접 열었다. C군에서 청록색이 망토·칼·소품에 나타나도 양손 청록 장갑 요구는 충족되지 않는다. C군 601020에는 요청하지 않은 칼과 손에 든 큰 가방이 보인다. 이 표본으로 모델 일반 성능이나 실패 확률을 추정하지 않는다.
- 전체 요구 통과 0/9는 최신 체크포인트의 기존 판정이다. 이번 담당이 9장을 모두 재채점하거나 GPU 비교를 다시 실행한 수치가 아니다.
- `model-ui/1440.png`, `design-revision/1440x900-compare.png`, `1440x900-comparison-to-edit.png`, `visual-check/verified-board.png`를 직접 열었다. 후자의 화면은 저장된 후보 복원·검수 화면이며 현재 서버의 실시간 실행 캡처가 아니다. 보드의 긴 반복 메모는 검수용 입력으로 보이며 사용자 행동 증거로 해석하지 않는다.
- 과거 실제 브라우저·GPU 인계는 후보 2개·부분 수정·파일 복원 성공과 그림 품질 미통과를 분리한다. 이번에는 해당 기능 테스트를 재실행하지 않았다.

## 비교 제품 선정과 공식 기능

ComfyUI는 현재 이미지 실행 기반이자 사용자가 언급한 작업공간 참고 대상이다. Krita AI Diffusion은 그림 편집 안에서 후보를 적용하는 흐름, InvokeAI는 캔버스 편집·이미지 관리·프로젝트 저장을 비교하기에 적합하다. 제품은 설치하지 않았으며 공식 문서의 현재 설명을 비교했다. 모든 외부 URL 확인일은 **2026년 10월 20일 KST**다. 문서가 기능을 설명한다는 사실과 설치 환경에서의 검증은 다르다.

## 개선안 세 가지

1. **요구를 보면서 비교하기.** 후보 생성 당시 설정과 실제 전달 문장을 확인하고, 필수 조건 최대 3개를 수동으로 미확인/충족/미충족 표시한다. 수정본은 이전 판정을 자동 승계하지 않는다. 비교 버튼이나 기록만으로 종합 품질 점수를 만들지 않는다.
2. **원본과 수정 부위를 함께 표시하기.** 부모 후보·수정 목표·현재 마스크를 같은 맥락에서 보여 주고 선택 영역으로 이동한다. 현재 후보 설정과 편집 중 지시의 차이를 알 수 있게 하되 작성 중 입력은 자동 교체하지 않는다. 부분 수정의 픽셀 보존과 시각적 요구 충족을 따로 확인한다.
3. **저장과 재개 범위를 분명히 하기.** 현재 프로젝트로 되살릴 후보/설정/기록과 다시 칠해야 할 마스크를 저장 전에 알린다. 보드에는 목표 설명과 미해결 메모를 구분하고 다음 수정할 후보·이유를 남긴다. 우선 기존 메모를 활용하며 저장 형식 확장은 총괄 계약으로 조정한다.

먼저 확인할 가설은 원본·수정 부위·미충족 요구를 함께 보이면 다음 수정 판단이 정확해진다는 것이다. 수용 기준은 원본/제출 ID 일치, 명시적 생성 전 요청 0회, 후보 전환 시 입력 보존, 미확인 판정 유지, 저장 범위의 정확한 안내다. [Live2D 편집 패턴](live2d-workflows.md)에 두 가지 초기안으로 좁혔다. 별도 구현·일정 확정은 아니다.

## 증거와 후속 범위

로컬 근거 경로·SHA256·열람한 이미지·외부 공식 URL과 확인일은 [research-evidence.json](research-evidence.json)에 있다. 생산 코드와 디자인 파일은 수정하지 않았다. 최신 환경 복구, 대회 요건, 모델/메모리/추론 가능성은 각 담당 범위다. 후속 교차 제품 아이디어 종합과 우선순위는 총괄이 맡는다.
