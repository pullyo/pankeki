## 2. 이번 기한의 완료 범위

**최신 착수 순서 정정:** 사용자가 실제 2D 움직임의 설계·실행계획과 기존 작업팀 구현을 승인했다. 부위 소재·제한된 메시/키폼·눈/입/호흡·재생·저장 재개의 첫 수직 흐름을 우선 구현 중이다. 전체 기능을 삭제하지 않으며 아래 날짜별 계획은 기존 견적이다. 새 담당별 착수/기술 검증 후 일정을 갱신한다. [누락 점검](plan-gap-audit-20261020.ko.md), [승인 설계](../superpowers/specs/2026-10-20-motion-first-design.md), [현재 기능 추적표](feature-delivery-tracker-20261020.ko.md)를 따른다. 단위 모듈의 통과를 앱 전체 완료로 판정하지 않는다.

최신 제품 우선순위는 **캐릭터 생성과 수정을 편하게 만드는 것**이다. 첫 화면과 첫 시연은 짧은 설명/내 그림 → 후보 비교 → 원하는 영역 수정 → 적용·되돌리기 → 저장·재개에 집중한다. 모델 평가는 수정 지시 준수·실패 및 재시도·대기 시간도 포함하며, 보기 좋은 생성 결과만으로 선정하지 않는다. 부위·움직임 계획은 이 흐름의 확장으로 유지한다. 새 구현 완료나 전체 일정의 단축을 뜻하지 않는다. 상세 기준은 [공통 제작 기획의 최신 사용자 방향](character-workflow-live2d-plan.ko.md#최신-사용자-방향-생성과-수정을-편하게)을 따른다.

목표 흐름은 **캐릭터 생성/가져오기 → 부위 준비 → 원본을 유지한 외형 조절 → 실제 눈·입·호흡 변형 → 표정 조합과 출력 → 저장 후 재개**다. 게임·웹툰·버튜버·마스코트의 공통 제작 과정을 유지한다.

| 필수 항목 | 10/30 완료로 인정할 결과 |
| --- | --- |

전체 확장 제품의 완성 범위는 더 크다. 이번 일정에서는 **수동 소재 준비와 제한된 변형 엔진**을 사용한다. 자동 파츠 분리·자동 리깅·큰 고개 회전·전신 포즈·머리카락 물리·얼굴 추적·PSD·Cubism 전용 파일·동영상 인코딩은 후속 범위다. 준비한 소재와 리그를 쓰면 그 수동 준비를 데모에서 알린다. PNG 교체·교차 페이드를 실제 메시 보간처럼 제시하지 않는다.

## 3. 작업량과 병렬 배치

아래는 견적이며 실측 완료 시간이 아니다. 작업일은 해당 담당의 집중 작업 단위이고, 항목별 시간을 직렬 합산하지 않는다.

| 작업 묶음 | 예상 작업일 | 겹쳐 진행할 작업 |
| --- | ---: | --- |
| 모델 비교·실행 환경·SDK 통합 | 1~2 | Codex 계약, 부위/리그 데이터 계약 |
| 최소 Codex 연결과 UI·통합 검증 | 4~5 | 부위·저장, 변형 모듈 개발 |
| 부위·프로젝트v2·실행 취소 | 2~3 | 변형 모듈, 문서·출력 준비 |
| 제한된 메시·키폼·3파라미터 | 3~4 | 부위 UI, 이미지 경로 검증 |
| 표정 조합·시트·프레임 출력 | 1~2 | 저장 복원·통합 회귀 |
| 최종 검수·설치 재현·제출 자료 | 2 | 각 담당의 차단 결함 수정 |

주요 의존 경로는 **공통 데이터 계약 → 부위/변형 모듈의 병렬 개발 → 조합·출력 → 전체 저장 복원과 검수**다. 최상단은 약0.5일, 부위/변형의 긴 쪽3~4일, 조합·출력1~2일, 검수2일로 **약6.5~8.5 집중 작업일**을 목표로 한다. 이는 모델·Codex가 병렬로 준비되고 21일의 기술 검증이 통과하는 조건부 견적이다. 10일 남짓의 달력에 들어갈 가능성은 있지만 여유가 크지 않다.

## 4. 날짜별 산출물과 종료 조건

**10/20 16:15 KST 갱신 — 오늘의 실행 목표:** 승인된 움직임 기능의 첫 실사용 흐름을 검증한 빌드를 확보한다. 모델 다운로드·native 비교와 첫 재생 시연은 이미 끝났으며 반복하지 않는다. 아래 날짜별 표는 최초 견적이고 오늘의 실제 진척·우선순위는 이 문단과 기능 추적표를 따른다.

1. 최신 공유 빌드에서 예제의 눈/입/호흡 조절과 재생·정지·재재생을 확인한다. 이미 통과한 영향 검사는 재실행하지 않는다.
2. 준비 PNG 부위 가져오기·메시/key 편집·undo와 실제 저장/다시 열기/자동복원을 검수한다. 단일 미분리 PNG 업로드를 다중 부위 준비 완료로 세지 않는다.
3. 실제 정지 PNG와48프레임 ZIP의 CRC·파일 수·이름·크기·알파·시간을 독립 확인하고, 취소/실패/상한에서 완성 파일이 내려오지 않음을 확인한다.
4. 실제 재생 속도와 입력 반응을 측정한다. 30fps/100ms는 목표이며 미달이면 값·조건을 기록한다. 발견 결함은 담당에게 최소 재현으로 배정하고 차단 결함을 수정한다.
5. 아지가 실제 프로젝트·PNG·ZIP 및 QA 보고서를 확인해 오늘의 통과/실패/미검증과 다음 담당을 정리한다. 검증이 끝나지 않은 항목은 완료로 바꾸지 않는다. 움직임의 추가 결함/보완과 전체 수용 목표10/21~22를 유지한다. F01~F09/D01/P01은 추적표에 계속 남긴다.

오늘 보고할 결과는 **최신 빌드 + 편집 가능한 프로젝트 + 실제 PNG/48ZIP + 검수 결과/남은 결함**이다. 이 목표는 앱 전체 또는 Codex/새 모델 SDK 통합의 당일 완료 약속이 아니다.

| 제품 기획·사용자 리서치 | 동일 제작 과제와 짧은 사용성 검토, 완료 판정·시연 문구 점검. 새 광범위 경쟁제품 조사를 추가하지 않음 |
| 출시·제출 준비 | 공개 후보·설치 안내·소스/라이선스·출처·시연·제출 폼 자료. 실제 공개/소셜/제출 권한과 준비를 구분 |

새 채팅·하위 에이전트를 늘리지 않는다. 제품 코드 작업은 파일 소유권이 나뉜 최대4개 기술 흐름을 기준으로 배치하며, 기존 8개 채팅을 8개의 독립 개발 스트림으로 계산하지 않는다. GPU는 한 번에 한 작업만 사용한다. 렌더/문서 계약을 먼저 맞춰 재작업을 줄이고, 같은 source revision의 이미 통과한 검사를 이유 없이 반복하지 않는다.

## 7. 최종 완료 판정과 관련 문서

- [ ] 실제 앱에서 공식 Comfy SDK를 통한 생성/부분 수정이 실행되고 결과·오류·취소가 맞다.

- [ ] 부위·마스크·알파·계층·편집·실행 취소가 저장/복원 뒤 유지된다.
- [ ] 같은 리그에서 눈·입·호흡의 중간 형태가 계산되고 새 이미지 추론 없이 조합·48프레임 출력이 된다.
