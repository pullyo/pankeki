# Pankeki 제품 목표와 차별화 우선순위

2026년 10월 20일 KST · 기획·리서치팀 1차 제안 · 총괄 검토 대기

Pankeki의 목표는 여러 창작 분야에서 쓸 오리지널 캐릭터의 콘셉트를 정리하고, 후보를 비교하고, 선택한 이미지의 일부를 고쳐 전달 자료로 저장하는 작업실이다. 현재 가장 큰 제품 문제는 생성 성공 후에도 색·소품 위치·재질 요구가 남는다는 점이다. **1순위는 후보별 요구 충족 여부를 사람이 기록하고, 미충족 항목 하나를 기존 부분 수정으로 이어 가는 흐름**이다. 이미지 자체의 품질 개선은 기능팀의 실험과 함께 판단한다.

## 유지할 사용자 결정

- 자유 창작·웹툰/웹소설·버튜버·마스코트·게임의 콘셉트 디자인을 지원한다. 특정 산업으로 축소하지 않는다.
- 밝고 정돈된 채팅 중심 화면, 큰 캔버스, 후보 비교, 마스크 부분 수정, 캐릭터 보드와 프로젝트 저장을 유지한다. 상세 설정은 보조 패널에 둔다.
- 대화 모델은 설정 정리와 요청 해석, 이미지 모델은 실제 생성·수정을 맡는 방향을 유지한다. 대화 미연결 상태와 실제 이미지 작업 상태를 명확히 표시한다.
- 현재 개발 중 공개 스냅샷이 있다는 결정을 유지한다. 이번 기획은 추가 게시·출품·모델 설치 지시가 아니다.
- 여러 시점·새 포즈의 동일 인물 보장, 3D·리깅·최종 제작 에셋 자동 완성은 첫 범위에 넣지 않는다.

결정 근거는 [공통 기준](../TEAM-CONTEXT.ko.md)의 최신 사용자 결정이며, 구현 상태는 [종료 체크포인트](../handoffs/shutdown-checkpoint.md)와 [재개 기능 인계](../handoffs/resume-function.md)를 우선한다. 예전 문서의 SDK 미구현·SD Turbo 기본값 설명을 현재 상태로 재사용하지 않는다.

## 새 모델 없이 가능한 과제 비교

아래 비용은 구현·기본 검증을 포함한 **기획 추정 인일**이다. 환경 복구, 실제 GPU 실험, 총괄 통합 검토 시간은 포함하지 않았다. 신규성이나 수상 가능성을 입증한 경쟁 조사 결과가 아니라 현재 실패에 대응하는 제품 후보 비교다.

## 1순위 최소 범위

### 사용 흐름

1. 기존 설정으로 후보를 만들거나 프로젝트를 불러온다. 후보 확인 영역에 생성 당시 브리프와 실제 전달 프롬프트를 보여 준다.
2. 사용자가 해당 후보에서 확인할 요구를 최대 3개, 각 120자 이내로 직접 적는다. 예시는 `양손에 청록 장갑`, `황동 플라스크가 벨트에 부착`, `가방이 무광 가죽으로 보임`이다. 자동 추출·이미지 이해를 전제로 하지 않는다.
3. 각 항목을 `미확인 / 충족 / 미충족`으로 사용자가 판정한다. 가려지거나 구분하기 어려우면 미확인으로 남긴다. `충족 1/3`처럼 사실만 표시하고 자동 품질 승인·종합 점수는 만들지 않는다.
4. 미충족 항목 하나의 `이 항목 수정`을 누르면 기존 `editCandidate` 경로로 해당 후보를 원본으로 연다. 선택한 요구를 수정 목표로 보여 주고, 사용자가 직접 마스크를 그린다. 추가 지시에 넣는 동작은 명시적 버튼으로 하며 기존 입력을 조용히 덮어쓰지 않는다.
5. 사용자가 실제 컴파일 프롬프트와 마스크를 확인하고 기존 생성 버튼을 누른다. 수정 목표 선택만으로 job을 제출하지 않는다. 기존 브리프와 추가 지시가 함께 전달되는 구조이므로 충돌하는 지시는 사용자가 확인할 수 있어야 한다.
6. 자식 후보가 준비되면 요구 문구만 복사하고 모든 판정을 미확인으로 시작한다. 부모 판정은 유지한다. 기존 비교로 부모와 자식을 확인한 뒤 다시 판정하고 프로젝트를 저장한다.

이 흐름은 채팅 패널 안의 보조 검수 UI와 기존 캔버스를 사용한다. 노드 화면이나 새 긴 설정 폼을 만들지 않는다. 로컬 대화 미연결 안내와 비활성 전송은 그대로 유지한다.

### 저장과 상태 계약 제안

후보의 생성 당시 `brief`, `request`, 이미지, `parentId`는 판정 때문에 변경하지 않는다. 사용자 판정은 별도 `review`로 보관한다. 항목마다 요구 문구, 세 상태 중 하나, 240자 이내 사용자 메모를 두고 후보당 최대 3개로 제한한다. 타임스탬프는 실제 수동 변경 시각만 기록한다.

현재 `profiles.js`는 알려지지 않은 candidate/project 필드를 거부한다. 따라서 메모를 임의 필드나 생성 측정값을 보관하는 metrics에 끼워 넣지 않는다. **새 review를 저장하는 프로젝트는 version 2로 구분하고 새 앱이 기존 version 1을 읽도록 하는 방향**을 제안한다. 옛 후보는 review 없음·미확인으로 읽고, 기존 앱이 version 2를 읽지 못한다는 점을 알린다. review와 입력 길이 검증, 자동 저장, export/import를 함께 바꿔야 한다. 이 형식과 DOM 추가는 총괄이 기능·디자인 담당과 확정할 공통 계약이며 아직 적용되지 않았다.

진행 중 후보 전환·원본 변경·프로젝트 불러오기 시 현재 revision 규칙을 적용한다. 대화 응답·수동 판정·실제 이미지 job 상태는 서로를 완료 처리하지 않는다. 입력 이미지·마스크는 현재처럼 exported request에 포함하지 않는다.

## 기능 품질 실험과의 관계

기능팀이 제안한 [다음 실험](../../work/team-resume/function/next-experiment.json)은 SDXL 가방 편집의 denoise 0.55 대 0.80을 비교한다. 본 기획은 그 조건·횟수·통과 기준을 변경하지 않는다. 총괄이 환경 인계를 확인해 실행 여부를 정한다. 결과가 좋아져도 장갑 색·소품 위치·전체 캐릭터 품질의 승인으로 확장하지 않는다.

제품 과제 1번은 실패를 기록하고 다음 수정을 돕는 개선이고, 기능 실험은 실제 편집의 재질 준수를 검사하는 별도 작업이다. 두 결과가 함께 있어야 제품 시연에서 사용자가 얻는 효과를 설명할 수 있다.

## 총괄 검토 후 다음 작업

총괄은 1순위 최소 범위와 저장 형식 변경 필요성을 검토하고, 채택할 경우 프론트엔드 담당에게 데이터·상태 처리, 디자인 담당에게 후보 확인 영역과 반응형 UI를 배정한다. 엔진 품질 실험은 기능 담당이 맡는다. 새 계약 확정 전 생산 코드를 변경하지 않는다. 검수팀은 위 표를 회귀 기준으로 사용하고, 출시팀은 [공식 제출 요건](contest-requirements-2026-10-20.ko.md)에 따라 실제 시연과 한계를 구분한다.

### 추가 담당 검토가 필요한 가정

기획팀 확대 지시를 반영해 기술 리서치 및 사용자·경쟁제품 리서치의 심층 조사는 별도 담당에게 둔다. 이 첫 기획안 작성 시 두 담당의 결과는 아직 읽지 않았다.

| 기획 가정 | 후속 검토 담당과 질문 |
| --- | --- |
| 사용자가 요구 3개를 수동 판정하는 부담보다 다음 수정 대상을 분명히 하는 이익이 크다. | 사용자·경쟁제품 담당: 실제 창작 흐름에서 판정·기록 수요가 있는지, 기존 도구와 어떤 차이가 의미 있는지 확인. 이 문서는 시장의 신규성을 주장하지 않는다. |
| 1순위 UI·저장 변경을 2~3인일에 수행할 수 있다. | 총괄·기능·디자인 담당: version 2 가져오기/내보내기와 자동 저장까지 포함한 작업량 재산정. |
| 기존 이미지 경로를 다시 사용할 수 있게 되면 부분 수정을 이어 갈 수 있다. | 기술 리서치·환경 담당: 현재 PC 제약과 기존 실행 환경의 복구 가능성을 확인. 모델·워크플로의 심층 비교는 이 문서에서 수행하지 않는다. |

후속 자료가 첫 가정을 반박하면 과제 순위나 범위를 총괄이 조정하되 기존 사용자 결정은 유지한다.

근거 목록과 이미지별 관찰은 [기획 증거](../../work/team-resume/planning/evidence.json), 실제 검증은 [기획 인계](../handoffs/resume-planning.md)에 남겼다.
