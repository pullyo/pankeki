# Live2D 편집 개념을 활용한 Pankeki 제품 아이디어

2026년 10월 20일 KST · 제품 기획 1차 제안 · 총괄 검토 대기

**우선 적용 후보는 수정 대상·바꿀 내용·유지할 내용을 한 번 확인하고 기존 부분 수정으로 이어 가는 흐름이다.** Live2D에서 가져올 핵심은 편집 대상과 기준 상태를 분명히 하는 작업 방식이다. Pankeki의 채팅·큰 캔버스·후보 비교·원본 보존·부분 편집을 유지하며, Cubism 런타임이나 자동 리깅을 도입하지 않는다. 기존 [제품 우선순위](resume-product-priorities.ko.md)의 요구 확인 과제를 구체화하는 제안이다.

## 공식 기능과 적용 해석

분석 대상은 사용자가 지정한 Cubism 5.3.04다. 공식 릴리스 목록은 해당 버전의 공개일을 2026년 9월 3일로 기록한다. 아래는 공식 Editor 5 매뉴얼의 편집 개념이며 5.3.04에 새로 추가됐다는 주장은 아니다. 설치된 Editor를 직접 조작하거나 바이너리 기능을 검증한 결과는 아니다. [공식 릴리스 목록](https://docs.live2d.com/en/cubism-editor-manual/new-feature-introduction-title/)

| 공식 문서에서 확인한 기능 | Pankeki에 적용할 해석 | 구분해야 할 한계 |
| --- | --- | --- |
| 선택한 오브젝트와 연결된 파라미터만 좁혀 보고, 기본 키폼을 잠그거나 기본값으로 되돌리는 기능이 있다. [Parameter palette](https://docs.live2d.com/en/cubism-editor-manual/palametorpalatte/) | 선택한 후보·수정 부위에 필요한 조작만 보여 주고 기준 원본을 분명히 둔다. | Pankeki의 마스크는 ArtMesh나 키폼이 아니다. 기본 상태 잠금이라는 편집 원칙을 참고한다. |
| 여러 키 편집 화면은 바뀌는 오브젝트와 바뀌지 않는 오브젝트를 나눠 보여 주고 적용 전후 값을 확인시킨다. [Multiple Keys Editing](https://docs.live2d.com/en/cubism-editor-manual/multi-key/) | 생성 전에는 수정 범위를, 생성 뒤에는 전후 이미지와 실제 보존 측정값을 보여 준다. | 요청 문구의 의미 보존과 픽셀 보존은 다르다. 마스크 안의 얼굴·재질 등을 문장만으로 잠글 수 없다. |
| 디포머는 묶인 메시의 변형을 함께 다루며 회전 디포머는 각도로 회전시킨다. [About Deformers](https://docs.live2d.com/en/cubism-editor-manual/deformer/) | 사람이 지정한 수정 영역에 이름을 붙여 반복 작업의 대상을 관리하는 아이디어로 연결한다. | 메시·변형 계층을 복제하거나 한 장의 이미지에서 자동 부품 분리를 한다는 뜻이 아니다. |
| 파라미터는 특정 움직임을 표현하고, 키에 등록한 형상 사이를 보간한다. [About Parameters](https://docs.live2d.com/en/cubism-editor-manual/parameter/) | 기준과 변형 후보를 변경 항목별로 묶어 비교하는 아이디어로 연결한다. | diffusion의 seed·denoise는 의미가 고정된 표정·재질 파라미터가 아니다. 슬라이더로 동일 인물·중간 형태·정확한 색을 보장하지 않는다. |

공식 기능은 위 문서가 뒷받침한다. 오른쪽 두 열은 Pankeki에 대한 기획 해석이며 Live2D가 이미지 생성 품질을 해결해 준다는 근거가 아니다.

## 아이디어 평가 기준

다음 기준은 두 리서치 담당의 결과를 받을 때도 동일하게 사용한다. 평가에 실제 사용자 측정이나 경쟁제품 점유율을 대입하지 않았다.

| 기준 | 채택에 필요한 근거 |
| --- | --- |
| 현재 범위 적합성 | 채팅·큰 캔버스·기존 후보·부분 수정·프로젝트 저장과 이어지고, 리깅·3D·새 포즈 보장을 요구하지 않는다. |
| 현재 실패에 대한 효과 | 청록 장갑·벨트 플라스크·가방 재질 실패 중 사용자가 어떤 문제를 더 잘 발견하거나 수정할 수 있는지 설명할 수 있다. |
| 실제 상태의 정직한 표시 | 미연결 대화, 생성 실패, 미확인 판정, 캐시 결과를 성공한 AI 작업과 구분한다. |
| 코드와 데이터 연결 | 원본 후보 ID·이미지·마스크·revision·request·parentId 중 무엇을 재사용하고 무엇을 새로 저장할지 특정한다. |
| 원본과 복원 신뢰성 | 다른 원본에 마스크나 판정을 잘못 재사용하지 않으며 옛 프로젝트 읽기와 새 저장 형식이 검증 가능하다. |
| 비용과 검증 가능성 | 저장 이미지로 먼저 확인할 수 있다. 신규 모델·대규모 패키지·GPU 반복 생성을 기본 전제로 삼지 않는다. |
| 사용자 부담과 차별화 | 수동 입력의 이익이 부담보다 큰지, 이미 널리 제공되는 기능과 어떤 차이가 있는지 별도 사용자·경쟁제품 담당이 확인한다. |

현재 범위 또는 실제 상태 표시 기준을 어기는 아이디어는 우선순위에서 제외한다. 나머지는 실패 대응, 현재 코드 재사용, 저장·검증 비용 순서로 비교한다. 수치 점수는 사용하지 않는다.

## 우선 아이디어와 후속 두 개

| 순위 | 아이디어와 추정 사용자 효과 | 현재 연결점 | 비용과 의존성 | 아직 필요한 검증 |
| --- | --- | --- | --- | --- |
| **우선. 수정 목표와 보존 범위 확인** | `가방 / 무광 빨간 가죽으로 / 얼굴과 망토 유지`를 한 작업으로 확인하고, 마스크·원본을 함께 본다. 잘못된 원본과 과도한 수정 범위를 줄일 것으로 예상한다. | `editCandidate`·`loadSource`, 현재 source/paint 캔버스, `requestSnapshot`, 실제 job 상태와 후보 비교. 기존 요구 확인 과제의 진입점으로 묶는다. | 중간. 프론트엔드·디자인의 작은 확인 영역과 상태 처리. 목표를 영구 보관하려면 기존 제안의 저장 형식 검토 필요. 생성 엔진 교체는 전제하지 않는다. | 사용자가 수정 부위를 정확히 이해하는지, 원본 전환 시 초안 무효화, 제출 전 요청 0회, 바깥 보존과 재질 판정을 구분하는지. |
| **후속 1. 이름 붙인 수정 영역** | `가방`, `왼손 장갑` 같은 수동 영역을 같은 원본에서 다시 불러 반복 선택 부담을 줄일 것으로 예상한다. | 현재 마스크 이미지·원본 후보 ID·sourceRevision/maskRevision. 현재 exported request는 source/mask를 제외한다. | 중간~큼. 이름·원본 식별값·해상도·마스크 데이터와 상한을 새 저장 계약에 포함해야 한다. 자동 분할 모델은 사용하지 않는다. | 다른 이미지·크기·후보에서 재사용 차단, 정확한 같은 원본에서 마스크 왕복 일치, 파일 크기 상한, 마스크 수정·삭제·옛 프로젝트 읽기. |
| **후속 2. 변경 항목별 기준과 후보 비교** | `가방 재질`을 검토 중인지 `장갑 색`을 검토 중인지 구분하고 선택 이유를 남긴다. 여러 요소를 한 번에 바꾼 비교의 혼동을 줄일 것으로 예상한다. | `parentId`, 생성 당시 `brief`·`request`, 2개 후보 비교, 선택 이력과 캐릭터 보드. | 중간. 후보 그룹과 변경 설명 메타데이터 필요. 저장된 후보부터 묶어 볼 수 있으며 자동 일괄 생성·보간은 필요하지 않다. | 같은 원본 여부와 설정 차이를 표시, 복수 설정 변경 시 단일 변수 비교로 표시하지 않음, 후보 선택·내보내기·판정 일치. |

비용은 정성적 기획 추정이다. 우선 아이디어는 앞선 요구 확인 과제를 구체화하므로 별도 대형 기능으로 중복 구현하지 않는다. 실제 이미지 재질 개선은 기능팀의 별도 실험 대상이다.

## 우선 아이디어의 최소 범위

1. 사용자가 기존 후보의 `이어서 수정`을 누르면 그 후보를 기준 원본으로 보여 준다. 수정 목표는 대상과 변경 내용 각각 한 문장, 유지할 내용은 선택 메모로 둔다. 대화 미연결 상태에서는 직접 입력한다.
2. 큰 캔버스에 현재 마스크를 보여 주고 `선택한 영역 수정 / 그 밖의 원본 보존`을 설명한다. 유지 메모가 마스크 안에 걸친 부분까지 자동 보호한다고 표시하지 않는다. 처음에는 실제로 그린 단일 마스크만 사용한다.
3. 추가 지시 반영은 사용자의 명시적 동작으로 한다. 기존 브리프·프롬프트를 조용히 바꾸지 않으며 실제 컴파일된 입력을 확인할 수 있게 한다. 원본 전환·프로젝트 불러오기 이후 예전 목표나 마스크를 자동 제출하지 않는다.
4. 사용자가 기존 생성 버튼을 누른 뒤에만 기존 SDK job 경로를 사용한다. 목표를 작성하거나 확인 영역을 여는 동작은 생성 요청을 보내지 않는다.
5. 결과에서는 원본과 자식 후보를 기존 비교로 보고 `수정 의도 충족`을 사람이 판정한다. 바깥 보존은 실제 측정값이 있을 때만 별도로 표시한다. 미측정 후보에는 보존 성공 배지를 붙이지 않는다.

가장 먼저 검토할 사례는 저장된 SDXL 가방 편집이다. 바깥 RGB 오차 0인데도 무광 가죽 요구는 실패한 결과를 사용해 두 판정의 차이를 이해하는지 확인할 수 있다. 현 단계에서 새 GPU 실행을 필요로 하지 않는다.

### 최소 검증 기준

- 후보 A를 수정 대상으로 선택한 뒤 B로 전환하면 A의 목표·마스크로 B가 제출되지 않는다. 진행 중 취소·늦은 응답의 기존 revision 처리가 유지된다.
- 목표 입력·범위 확인·판정 조작만 수행한 동안 `/api/jobs` 제출은 0회다. 실제 생성과 확인 UI의 상태가 분리된다.
- 원본·생성 후보·기존 비교·프로젝트 저장을 유지한다. 수정 목표를 저장할 경우 새 저장 형식과 v1 가져오기 검증을 함께 한다.
- 저장 가방 사례에서 `바깥 보존 확인`과 `재질 미충족`을 동시에 표현할 수 있다. 사용자 판정을 자동 성공으로 바꾸지 않는다.
- 1440px/390px와 키보드에서 목표 입력·범위 확인·결과 비교를 마칠 수 있다. 새로운 긴 폼이나 노드 편집기가 주 화면을 차지하지 않는다.

## 두 리서치 결과를 받을 때 확인할 연결점

첫 작성 시 `live2d-transfer.md`와 `live2d-workflows.md`는 작업 폴더 검색에서 아직 확인되지 않았다. 아래는 검토 기준이며 해당 담당의 결론을 대신 작성한 내용이 아니다.

| 입력 자료 | 제품 검토에서 확인할 질문 | 순위를 바꿀 수 있는 조건 |
| --- | --- | --- |
| 기술 담당 `live2d-transfer.md` | 파라미터·디포머에서 작업 방식만 가져오는 부분과 SDK/모델 데이터가 필요한 부분이 구분됐는가. 현재 PC·프로젝트 구조에서 원본 식별과 마스크 저장이 가능한가. | 우선 아이디어가 실제로 새 런타임·모델이나 원본 보존 계약 변경을 필요로 하면 더 작은 범위로 줄인다. |
| 사용자 담당 `live2d-workflows.md` | 대상 선택·기준 상태 복귀·수정 전후 확인 중 어떤 흐름이 현재 사용자의 반복 작업을 가장 줄이는가. 수동 목표 입력이 기존 상세 설정과 중복되는가. | 수동 입력 부담이 더 크다는 근거가 나오면 목표를 기존 요구 확인 항목에서 고르게 하고 새 입력을 줄인다. |

두 자료가 도착하면 이 기준으로 효과·의존성·검증을 갱신한다. 총괄은 그 결과와 함께 우선 아이디어를 기존 요구 확인 최소 범위에 포함할지 판단한다. 지금은 아이디어 제안까지 완료하며 구현·설치·자동 리깅은 진행하지 않는다.
